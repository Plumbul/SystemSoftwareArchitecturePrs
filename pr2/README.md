### 1. Напишіть програму для визначення моменту, коли time_t закінчиться. Дослідіть, які зміни відбуваються в залежності від 32- та 64-бітної архітектури. Дослідіть сегменти виконуваного файлу.

Для виконання завдання була реалізована програма. Оскільки мій пристрій має 64-бітову архітектуру, на ньому. Для тестування 32-бітової архітектури було необхідно встановити необхідний пакет за допомогою команди 
```
sudo apt install gcc-multilib
```
Також був використаний відповідний прапорець 
```
-m32
```
#### Код програми
```c
#include <stdio.h>
#include <time.h>
#include <stdint.h>

int main() {
    time_t t;
    int bits = sizeof(t) * 8;
    
    printf("Architecture: %d-bit\n", bits);

    long long max_seconds = (1LL << (bits - 1)) - 1;
    printf("Mathematical max seconds: %lld\n", max_seconds);

    time_t test_time = (time_t)max_seconds;
    struct tm *time_info = gmtime(&test_time);

    while (time_info == NULL && test_time > 0) {
        test_time >>= 1; 
        time_info = gmtime(&test_time);
    }

    if (time_info != NULL) {
        printf("Last processable date by your system (UTC): %s", asctime(time_info));
        printf("Corresponding seconds: %lld\n", (long long)test_time);
    } else {
        printf("Error: Could not convert any positive time value.\n");
    }

    return 0;
}
```

#### Висновок
Були досліджені відмінності поведінки типу даних time_t в залежності від архітектури:
- 32-бітна архітектура - оскільки time_t має розмір 4 байти, він переповнюється 19 січня 2038 року, після чого час "відкочується" у 1901 рік;

Теоретично це розширює межу часу роботи архітектури на сотні мільярдів років, і хоча є бібліотеки по типу GMP де можна працювати з числами будь-якої довжини, але стандартна бібліотека glibc, яка оперує датами, має логічне обмеження у 1.1 мільярдів років для запобігання помилкам в алгоритмах календарних розрахунків.

### 5. Відомо, що при виклику процедур і поверненні з них процесор використовує стек.Чи можна в такій схемі обійтися без лічильника команд (IP), використовуючи замість нього вершину стека? Обґрунтуйте свою відповідь та наведіть приклади.
Ні, у практичній реалізації архітектури процесора повністю обійтися без лічильника команд, замінивши його лише вершиною стека, неможливо. Головна причина полягає у функціональному розділенні завдань: лічильник команд забезпечує автоматичну лінійність виконання (адреси $n, n+1, n+2$), тоді як стек працює за принципом LIFO для збереження тимчасових даних. Якщо об’єднати ці поняття, будь-яка операція збереження локальної змінної або параметра (PUSH) автоматично змінювала б адресу наступної інструкції, що призвело б до хаотичного переривання логіки програми та неможливості написання звичайного послідовного коду.
З точки зору апаратної ефективності, використання стека як єдиного джерела адреси наступної команди змушувало б процесор звертатися до оперативної пам'яті перед кожним кроком, що критично сповільнило б роботу. Сучасні процесори використовують IP для випереджального читання команд (префетчінгу) та конвеєризації, що було б неможливо при постійній зміні вершини стека. Навіть у спеціалізованих "стекових машинах" (наприклад, Forth-процесорах або JVM) лічильник команд зберігається як окремий механізм для керування потоком виконання, тоді як стек залишається виключно інструментом для маніпуляції операндами.
Єдиним прикладом, де вершина стека фактично диктує значення лічильника команд, є операція RET. Під час її виконання процесор копіює адресу повернення зі стека безпосередньо в регістр IP. Проте побудова всієї програми виключно на такому принципі перетворила б кожну інструкцію на примусовий перехід, роблячи структуру коду надмірно складною, а використання кеш-пам’яті — неефективним. Отже, розділення IP (курс виконання) та SP (сховище даних) є фундаментальною умовою стабільної та швидкої роботи обчислювальних систем.

### 4. Дослідіть техніки розподілу пам’яті в багатопотокових програмах.
У багатопотокових програмах техніка розподілу пам'яті стає критичним вузлом продуктивності через проблему конкуренції за блокування (lock contention). Коли кілька потоків одночасно намагаються виділити пам’ять через стандартний системний виклик malloc(), вони змушені чекати на звільнення глобального блокування (mutex), що зводить нанівець переваги паралелізму.
Однією з основних технік вирішення цієї проблеми є використання арен або локальних кешів потоків (Thread-Local Storage, TLS). У таких системах, як tcmalloc (від Google) або jemalloc (використовується у FreeBSD та Facebook), кожен потік отримує власну невелику ділянку пам'яті, з якої він може миттєво виділяти об'єкти без звернення до глобального менеджера. Тільки коли локальна арена вичерпується, потік звертається до центральної купи за новою порцією пам’яті, що значно знижує кількість блокувань.
Іншою важливою технікою є поділ об'єктів за розміром (Slab allocation). Пам’ять розбивається на сторінки, кожна з яких містить об’єкти лише одного конкретного розміру. Це мінімізує зовнішню фрагментацію та дозволяє потокам швидше знаходити вільні слоти. Також розробники застосовують структури даних без блокувань (lock-free structures) на базі атомарних операцій (наприклад, CAS — Compare-And-Swap), що дозволяє керувати списками вільних блоків пам'яті без використання класичних м'ютексів.
Окрему увагу приділяють боротьбі з ефектом помилкового розділення (false sharing). Це ситуація, коли два потоки працюють з різними змінними, але ці змінні випадково опинилися в одному кеш-рядку (cache line) процесора. У такому разі система змушена постійно синхронізувати кеші між ядрами, що сповільнює роботу в десятки разів. Для запобігання цьому використовується вирівнювання пам'яті (padding/alignment), щоб критичні дані різних потоків гарантовано потрапляли в різні кеш-рядки.
