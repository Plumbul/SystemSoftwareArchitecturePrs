### Завдання 4.1 
#### Скільки пам’яті може виділити malloc(3) за один виклик?
#### Відповідь
Теоретичний ліміт malloc визначається максимальним значенням типу size_t, яке для 64-бітних систем становить 2<sup>64</sup> −1 байт. На практиці обсяг обмежений розміром віртуального адресного простору процесу (зазвичай до 128 ТБ на архітектурі x86-64 через фактичне використання лише 48 бітів для адресації, половина з яких зарезервована для потреб користувача), обсягом фізичної оперативної пам'яті разом із файлом підкачки та системними лімітами (RLIMIT_AS). В ОС Linux через механізм overcommit malloc може успішно повернути вказівник на обсяг, що перевищує фізичні ресурси, проте при спробі запису даних процес буде завершено OOM Killer. Якщо запит неможливо задовольнити на рівні адресного простору або через обмеження ОС, функція повертає NULL.

### Параметр malloc(3) є цілим числом типу даних size_t, тому логічно максимальне число, яке можна передати як параметр malloc(3), — це максимальне значення size_t на платформі (sizeof(size_t)). У 64-бітній Linux size_t становить 8 байтів, тобто 8 * 8 = 64 біти. Відповідно, максимальний обсяг пам’яті, який може бути виділений за один виклик malloc(3), дорівнює 2^64. Спробуйте запустити код на x86_64 та x86. Чому теоретично максимальний обсяг складає 8 ексабайт, а не 16?\
#### Код програми
```с
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>

int main() {
    size_t step = 1024ULL * 1024 * 1024;
    size_t current_request = step;
    void *ptr = NULL;

    printf("--- Malloc Limits Testing ---\n");
    printf("Size of size_t: %zu bytes\n", sizeof(size_t));

    while (1) {
        ptr = malloc(current_request);

        if (ptr != NULL) {
            printf("[SUCCESS] Allocated: %zu GB\n", current_request / (1024 * 1024 * 1024));
            free(ptr);
            
            if (current_request > (SIZE_MAX - step)) {
                printf("Reached SIZE_MAX limit!\n");
                break;
            }
            current_request += step;
        } else {
            printf("[FAILED] Could not allocate: %zu GB\n", current_request / (1024 * 1024 * 1024));
            
            if (step > 1024 * 1024) { 
                printf("Refining search with smaller steps (1 MB)...\n");
                current_request -= step;
                step = 1024 * 1024;  
                current_request += step;
            } else {
                printf("Final limit reached at approximately: %zu MB\n", current_request / (1024 * 1024));
                break;
            }
        }
    }

    return 0;
}
```

#### Висновок
Теоретичний ліміт malloc(3) визначається максимальним значенням типу size_t, що для 64-бітних систем становить 2^64−1 байт (16 ексабайт). Однак на архітектурі x86-64 фізично реалізовано лише 48-бітну адресацію, яка обмежує загальний простір до 256 ТБ, а через поділ на простір користувача та ядра програма отримує лише нижню половину — 128 ТБ (саме тому ліміт становить 8 ексабайт у теорії канонічних адрес, а на практиці ще менше). Hезультати запуску програми показали обмеження у 2 ГБ на обох архітектурах свідчать про те, що на x86 це архітектурна межа адресного простору, а на x86_64 — це ліміт фізичних ресурсів та політика overcommit_memory вашої ОС, яка забороняє виділяти віртуальні адреси, що занадто сильно перевищують реальні можливості заліза. Таким чином, хоча size_t дозволяє передати величезне число, malloc поверне NULL, як тільки вичерпається або віртуальний адресний простір процесу, або ліміт доступної системної пам'яті.

### Завдання 4.3
Чи є помилки у такому коді?
```с
void *ptr = NULL;
while (<some-condition-is-true>) {
    if (!ptr)
        ptr = malloc(n);
    [... <використання 'ptr'> ...]
    free(ptr);
}
```
Напишіть тестовий випадок, який продемонструє проблему та правильний варіант коду.
#### Відповідь
Головна помилка коду полягає у виникненні висячого вказівника. Оскільки функція free(3) звільняє пам'ять, але не обнуляє саму змінну-вказівник, перевірка if (!ptr) на наступних ітераціях дає хибнопозитивний результат. Це призводить до небезпечного використання вже звільненої пам'яті та фатальної помилки Double Free при спробі повторного виклику звільнення. Для виправлення необхідно або обнуляти вказівник одразу після звільнення, або переглянути архітектуру циклу, винісши операції виділення та звільнення за його межі.
#### Код програми
```с
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

void broken_code() {
    void *ptr = NULL;
    int i = 0;

    printf("--- Running Broken Code ---\n");
    while (i < 2) {
        if (!ptr) {
            ptr = malloc(100);
            printf("Iteration %d: Allocated at %p\n", i, ptr);
        } else {
            printf("Iteration %d: Using OLD pointer %p (Danger!)\n", i, ptr);
        }

        strcpy((char*)ptr, "Data"); 
        
        printf("Iteration %d: Freeing %p\n", i, ptr);
        free(ptr); 
        i++;
    }
}

int main() {
    broken_code();
    return 0;
}
```

#### Правильний варіант коду 
```с
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

void fixed_code() {
    void *ptr = NULL;
    int i = 0;

    printf("--- Running Fixed Code ---\n");
    while (i < 2) {
        if (!ptr) {
            ptr = malloc(100);
            if (!ptr) return;
            printf("Iteration %d: Allocated at %p\n", i, ptr);
        }

        strcpy((char*)ptr, "Safe Data"); 
        
        printf("Iteration %d: Freeing %p and nullifying\n", i, ptr);
        free(ptr); 
        ptr = NULL;
        i++;
    }
}

int main() {
    fixed_code();
    return 0;
}
```

Це гарантує, що на кожній наступній ітерації умова if (!ptr) буде істинною, що змушує програму виділяти нову ділянку пам'яті. Це повністю усуває проблему "висячих вказівників" та гарантує стабільну роботу менеджера пам'яті.
### Завдання 4.5. Що станеться, якщо realloc(3) не зможе виділити пам’ять? Напишіть тестовий випадок, що демонструє цей сценарій.
#### Відповідь
Якщо функція realloc(3) не може виділити новий блок пам'яті (наприклад, через брак ресурсів або занадто великий запит), вона повертає NULL. Найважливішим моментом є те, що при цьому старий блок пам'яті не звільняється і залишається валідним. Головна помилка програмістів полягає у присвоєнні результату realloc безпосередньо старій змінній (наприклад, ptr = realloc(ptr, size)). Якщо повернеться NULL, адреса старого блоку буде втрачена, що призведе до витоку пам'яті.
#### Код програми
```с
#include <stdio.h>
#include <stdlib.h>

int main() {
    size_t initial_size = 1024;
    void *ptr = malloc(initial_size);
    
    if (!ptr) return 1;
    printf("Initial pointer: %p\n", ptr);

    size_t extreme_size = (size_t)-1 / 2; 
    printf("Attempting to realloc to a huge size...\n");

    void *tmp = realloc(ptr, extreme_size);

    if (tmp == NULL) {
        printf("realloc(3) failed: returned NULL\n");
        printf("Status: Original pointer %p is still valid and NOT leaked.\n", ptr);
        free(ptr);
    } else {
        ptr = tmp;
        printf("realloc(3) succeeded at %p\n", ptr);
        free(ptr);
    }

    return 0;
}
```

Якщо ж одразу перезаписати початковий вказівник значенням NULL, яке поверне realloc, доступ до раніше виділеної пам'яті буде назавжди втрачено, хоча вона залишатиметься зайнятою в системі.
